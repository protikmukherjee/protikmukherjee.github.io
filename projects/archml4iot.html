ArchML4IoT, Architecture DSL for IoT Twins

A domain-specific architecture-modelling language and toolchain that takes a high-level IoT architectural specification and compiles it down to executable statecharts and configuration artifacts. Accepted at ANNSIM '26.

Year
2025 – Now
Role
Co-developer
Lab
Software Modelling Lab, TMU
Venue
ANNSIM '26 (accepted)

§ 01

The problem

IoT system descriptions live in three places that drift out of sync: a Word document the architect wrote, a config repo the engineer maintains, and the runtime behaviour the system actually exhibits. When something breaks, no one knows which version is "true."

We wanted a single source of truth, a language that captures the IoT architecture at the level architects actually think (devices, subsystems, communication topology, behaviour modes) and that compiles down to runnable artifacts without losing fidelity.

§ 02

The language

ArchML4IoT lets you describe IoT subsystems aligned with the IoT Architectural Reference Model, their state machines, communication channels, and operational modes, in a concise DSL. From a single spec, the toolchain automatically instantiates reusable behavioural templates from the STL4IoT library to generate:

  • Executable statecharts per subsystem
  • Configuration artifacts for the runtime (channels, topics, schedules)
  • A simulation-ready statechart project usable for design-time analysis before you deploy

The smart-home twin (see the case study) became the testbed: the same four-ESP32 architecture was re-expressible in ArchML4IoT and the generated artifacts matched the hand-written versions.

§ 03

Why a DSL

You can build IoT systems by gluing YAML to scripts to firmware, and many people do. But once you have a DSL, three things change.

First, the spec is the contract. The architect's intent and the engineer's implementation can't diverge silently because both fall out of the same source. Second, you get analysis for free, model-checking, reachability, dead-state detection, because the spec is in a form a tool can reason about. Third, the spec is the documentation. New engineers read the DSL file, not a stale README.

§ 04

Where it's going

The ANNSIM '26 paper introduces the language and the simulation-model generation pipeline. The next milestones I'm working on: model-checking against safety properties (e.g., "alarm always precedes evacuation transition"), and continuous drift monitoring between the DSL spec and the running system's actual behaviour traces.
